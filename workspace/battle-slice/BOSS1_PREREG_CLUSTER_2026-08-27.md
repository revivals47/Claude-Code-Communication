## 規則 (これを次回そのまま適用する)

**hp event の 時刻の空きが 0.5 秒を超えたら、そこを「発」の境界とする。**

- 対象 = worker2 の watcher が出す `kind == "hp"` の event 列、unit ごとに独立に束ねる。
- 1 発の ΔHP = その束の 最初の event の `prev` − 最後の event の `hp`。
- 束ね直し・窓の再選択は しない。

## 根拠 (2026-08-27 の 1 戦闘の実測。表示値を使わずに hp event の時刻だけから出したもの)

- 1 発の内側の event 間隔 = 中央値 **0.052 秒**
- 発と発の間の 最小の空き = **2.045 秒**
- 谷の比 = 2.045 / 0.052 = **39 倍**
- 窓を 0.3 / 0.5 / 0.8 / 1.0 / 1.5 / 2.0 秒 に振ると **すべて同一の 7 値** (86/78/84/75/85/86/6)
- 3.0 秒で崩れる (末尾 3 発が併合して 177 = 85+86+6)

**0.5 を選ぶ理由** = 下に 10 倍 (0.052)、上に 4.1 倍 (2.045) の余裕。
前回 boss1 が使った 2.0 は 上端まで 2.2% しかなく、境界に近すぎた (boss1 自己申告)。

## 前回の弱点として明示的に引き継ぐもの

1. **前回の窓 2.0s は 表示値を見た後に決めた (事後)**。
   ただし robustness 検査自体は **表示値を一切使っていない** (hp event の時刻のみ) ので、
   「7 値が hp データだけで決まる」という主張は事後性に汚染されていない。
2. **本当に弱いのは「0 が 3 個」の置き場所**。
   hp データが言うのは「32.5 秒 動かなかった」だけで、「3 発 外した」とは言っていない。
   **3 という数は 表示側から来ている**。独立な裏づけなし。
   ただし当該 3 発は器が「評価不能」にするため 6/6 の一致には 1 発も寄与していない。
3. この事前登録が塞ぐのは「窓の値の選び直し」まで。
   **「別の束ね方の族をいくつか試して合った方を出す」は これでは塞げない** (worker1 指摘)。
   ゆえに 族ごと 今 登録する = 上の規則以外は使わない。

# 追補 (同日・次の戦闘のデータは依然 1 byte も存在しない)

worker1 提案の 3 件を採用して追加登録する。理由 = 本体の規則だけでは
「外れたの判定が事後の目分量」「0 の置き場所が未登録」「範囲攻撃が未登録」の 3 つが空いていた。

## (A) 「規則が外れた」の判定を **表示値を見る前に** 済ませる

次の戦闘の hp event 列に対し、**表示値を一切使わずに** まず次を測る:

- 束の内側の 最大の空き
- 発と発の間の 最小の空き

**適用条件: 束の内側の最大の空き < 0.5 < 発の間の最小の空き**

- 成り立つ → 規則を適用して束ねる。
- **成り立たない → 「この戦闘には規則を適用できない」と報告し、束ねない。**
  窓を選び直さない。別の族に乗り換えない。

## (B) 「0」(damage 0 の表示) の置き場所

- **本命 (表示呼び出しの a0/a3 捕獲) が効いた場合** = 0 は **捕った呼び出しの順** に置く。
- **本命が効かなかった場合** = **0 は置かない。評価不能のまま残す。**
  (前回の「32.5 秒の空白に 3 個」は hp 側に裏づけが無い推測だった。同じ推測を繰り返さない。)

## (C) 範囲攻撃 (1 発が複数体を削る)

本体の規則は unit ごとに独立に束ねるため、1 発が 2 体を削ると **束は 2 つ・表示は 1 個** になりうる。

- **複数 unit の束が同じ時刻窓に重なったら、合計せず「評価不能」で報告する。**
- 合計してはならない理由 = 合計すると検定 1 (Σ D_n vs Σ ΔHP) が **見かけ上通ってしまう**。

## 追補の位置づけ

(A)(B)(C) はいずれも worker1 発案、boss1 採用。
**3 件とも次の戦闘のデータが存在しない時点で登録した。**
