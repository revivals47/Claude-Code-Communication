## 限定（worker1 が明記、そのまま保持）

1. **「容疑集合」であって確定ではない** — 同じ field を複数 opcode が動かす
2. ~~`0x64` の pending 書き site は個別に同定していない~~ → **解消**（§260、下記）
3. `0x2A` / `0x2B` の金 counter (`gp-0x6b78` = `0x8013E294`) は**出力されていない** —
   ただし **vmtrace の read 範囲(`0x8013E100`+`0x200`)の中にある**（worker2 訂正）。
   ∴ 障害は read コストではなく **vmtrace の sha 凍結**（v4 / v5 が流通中）。`FIELDS` に 1 行足すだけで済むが、**既存 run からは復元できない**
4. **`win[4]` / `win[5]` を引かないこと** — 窓ではない（上表参照）。引くと `0x27` を追って**何も見つからない**

### 「実装済だが型が違う」3 例目

```
原盤 : 0x64 handler (0x800EDEDC) は pending = 0x64 を 6 経路で書く
remake: case OP_CASCADE(0x64) = StoryState(-0x6d90) の var-write のみ ⇒ pending を書かない
```

`pending != 0` なら **VM は何も実行せず返る**（§232.2）。
∴ **原盤は 0x64 の後 VM が止まり、remake は止まらない** = **挙動差の候補**。

**(462) により今は直さない。** ① が `pending` の差を指したら**即座に 0x64 に帰属できる**ことが成果。

## 絞り方 — 限定 1（容疑集合であって確定でない）を減らす（§261、**追加観測ゼロ**）

### `depth` が動いたとき → record の `+6` tag で絞る

record layout（§157 / §160 確定）= `+0` 戻り PC(u32) / `+4` entry id(u16) / **`+6` tag** / `+7` section id

| tag | opcode |
|---|---|
| 1 | `0x13` `0x14` |
| 3 | **`0xFB` のみ** |
| 4 | `0x4B` `0x7B` `0x58` `0x66` |
| 0 | 番兵 |

**さらに絞る規則**（§160、push 6 件全数）: **`+0..+5` を埋めるのは `0x13` だけ**

- tag 1 かつ `+0`/`+4` が**埋まっている** ⇒ **`0x13`**
- tag 1 かつ `+0`/`+4` が **0** ⇒ **`0x14`**

∴ **push 7 opcode → tag で 3 群 → `+0`/`+4` で `0x13`/`0x14` を分離**。
**vmtrace は `STACK_BASE = 0x801639E0` を既に読んでいる ⇒ 追加観測ゼロ**。

**限定**: `STK_LEN = 0x2A0` ⇒ STACK_BASE から **`0x40` = 8 record 分**まで。観測 depth 最大 2 なので足りるが、**深さ 8 超は採れない**。
**tag 4 の 4 opcode は tag だけでは分離できない**（`+7` section id で更に絞れるかは**未検定**）。

### `VAR_*` が動いたとき → var index で絞る

- **`var[0]`** = **VM 退出後処理のみ**（§232.2 の `0x800F0CD0(a0=0, a1=[0x8013E14F])`）⇒ **opcode 由来ではない = 容疑から外せる（確定）**
- `var[op]` = `0x22` `0x25` `0x3F` `0x7B`（§254 で各々の a0 を確定）/ `0x1E` `0x1F` `0x20`（set / add / sub）

### 絞れない所（worker1 が明記）

- **`pc`** = 全 opcode。絞れないし絞る意味もない
- **`stop` → 1** = band 外 opcode 全部。絞れない
  - ただし §248 の実測で**到達する band 外は `0x0C` / `0x0E` の 2 種のみ**（section 0x0B 由来）⇒ 実務上は 2 種（**母数は worker1 の census**）
- **`WIN_*`** = slot0-3 のみ（上表・限定 4 参照）

## `pending` の未観測 2 値 — **理由が別**（worker2、§0x64 母数）

**母数 = 989 観測**（run1 96 / run4 545 / runA 23 / runB 25 / burst 300）
**出現 5 値** = `0x00` `0x10` `0x1A` `0x4A` `0x67` ⇒ **未観測 = `0x64` と `0xFF` の 2 つ**

| 値 | 不在の理由 | 接地 |
|---|---|---|
| **`0xFF`** | **機構で塞がっている**（window gate bit6 が開かない） | **3,792 観測で bit6 = 0** |
| **`0x64`** | **捕獲した場面で実行されていない公算** | **989 観測で不在** + 滞在時間の類推 |

**「取りこぼしただけでは?」を worker2 が自分のデータで検定**:
非零 pending の閉じた区間 12 本の滞在時間 = **最短 50 ms / 最長 2,257 ms**（1 kHz ⇒ **最短でも約 50 標本**）。
∴ **この field は 1 frame で消える種類ではない** ⇒ `0x64` が同類なら 1 kHz で見落とす公算は低い
⇒ **「不在 = 実行されていない」の方が説明として強い**。
**ただし同類かは未検証**（観測 5 値からの類推。`0x64` の滞在時間は測っていない）。

**事実（worker2、判断も発注もしていない）**: `0x64` を通る場面を撮れば **2 つ同時に埋まる** —
① E5 の最後の到達可能な空欄 / ② worker1 の「型が違う」3 例目の観測場所。
