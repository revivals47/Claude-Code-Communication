⚠ **数値は必ず (設定 / 単位 / 値) の 3 つ組で書く。1 つでも欠けたら比較表に載せない。**

- **単位**: `byte` / `個`(opcode 種)/ `site`(命令の所在)/ `pc`(到達点)/ `件`(その他)。
  単位を書かない数値は、**足し合わせた瞬間に意味を失う**(実例: 命令 `pc` 数と TEXT `byte` 数を同じ分子に足した指標が 6 便生きた)。
- **設定**: 同じ量でも walker の設定(`BAND_OUT_TERM` の 0/1 など)で値が変わる。
  設定を書かない数値は、**並べた瞬間に順位が入れ替わる**
  (実例: 設定を揃えると worker1 と worker3 の差は **1.83 pt → 0.38 pt**、外れ値は別の者に移った。
  同じ罠を 2 度、別の者が踏み、**2 度とも止めたのは第三者**。注意では止まらない)。

⚠⚠⚠ **率で比較しない。byte で出す。**
被覆率の分母は `総 − 先頭表 − TEXT extent` だが、**`TEXT extent` は walker 自身の出力**である。
⇒ 到達が減ると TEXT も減り分母が増えるので、**率は二重に動く**。
実測: 同一 walker の bound を 3 端に振ると **分母が 141,754 byte 動いた**(590,040 / 448,286 / 528,326)。
⇒ **端ごとに分母が違う量は、区間として読めない。**
⇒ ★**本 session で出た pt 単位の比較(10.73 pt / 1.57 pt / 0.38 pt など)は、すべてこの欠陥の上に立っていた**★。
byte 単位の量(spread 8,798 byte 等)は影響を受けない。

⚠ **率をどうしても書くときは 6 つ組が要る: (値 / 単位 / 母集団 / 基底 / bound / 別枠)。**
`bound` = 解析器が置いた打ち切り(§6 `0x19` のように **静的に決定不能な量には必ず付く**)。
`別枠` = **その bound が extent を決めてしまった量**(= 未確定量)。

⚠⚠ **`別枠` と `感度` は別物。混ぜない。**
- `感度` = bound を**動かしたときに変わる**量。
- `別枠` = bound が**決めてしまっていて、動かしても変わらない**量。
⇒ ★**「動かしても変わらない」ことと「確かである」ことは別**★(worker3)。
実例: 区間の幅 **0.80 pt** に対し別枠 **23.51%(36,785 byte)** — **区間は不確かさを表しきれない**。
逆に「感度 0」も「死んでいる」ではなく「**余裕がある**」場合がある(worker1: step 上限を 500 まで下げると −24,664 byte)。

⚠ (旧 4 つ組の記述。上の 6 つ組に置換済)
上の 3 つ組は **他者と並べるとき**の規約、こちらは **率そのものを書くとき**の規約。**軸が違うので統合しない**。
(実例: 同じ量が「全サイズ 1,854 byte」と「256 byte 以上に絞って 1,515 byte」で 339 byte ずれ、
**母集団を絞ったことを同じ行に書いていなかった**ために別人の誤りに見えた。)

## 1. 実行の外枠

```
外側関数 0x801184E8
  ├ jal 0x800FA5E4
  ├ jal 0x80105268
  ├ lw v0, 停止flag ; bne v0,zero → skip      ← ★flag != 0 なら VM を呼ばない★
  └ jal 0x800F027C (VM)                        ← ★loop なし = 1 フレーム 1 回★
```

- VM 本体 = `0x800F027C`。**caller は 2 件のみ**(`0x800F0170` / `0x801185A0`)。
  - 全数根拠: `jal` 全走査 + **materialize 検定**(VM address は data 語 0 / lui+addiu 0)。
  - 陽性対照: jmp_buf `0x80164068` = 37 件 / entity base `0x80145608` = 45 件 ⇒ 検出器は動く。
- **VM は 1 フレームに 1 回しか回らない。** yield すると次フレームまで待つ。
- ⚠ **flag の gate は caller 固有ではない。** VM 入口 `0x800F027C` 自身(`0x800F028C`–`0xA0`)も flag を見て即 return する。

(経路 B = 7 本の RAM dump で停止 flag がきっかり 0 か 1。)

## 3. dispatch(router `0x800F0744`)

opcode fetch = `0x800F0780`〜: `lw PC / addiu +1 / sw PC / lbu (PC)`。**opcode 1 byte を消費**。

判定は全 band 同一形: `sltiu at,s0,LO → bne(次へ)` / `sltiu at,s0,HI → beq(次へ)` = **半開区間 [LO,HI)**。

| band | opcode | 個数 | band handler | jump table base |
|---|---|---|---|---|
| 1 | `0xFB`–`0xFF` | 5 | `0x800EC404` | **表なし(inline beq)** |
| 2 | `0x10`–`0x27` | 24 | `0x800EC4AC` | `0x8011B0F8` |
| 3 | `0x28`–`0x3F` | 24 | `0x800ECAB4` | `0x8011B1A0` |
| 4 | `0x46`–`0x58` | 19 | `0x800ED434` | `0x8011B200` |
| 5 | `0x5A`–`0x5F` | 6 | `0x800EDD88` | `0x8011B24C` |
| 6 | `0x64`–`0x7E` | 27 | `0x800EDE88` | `0x8011B3A0` |

**合計 105 個 / band 外 151 個**(opcode 種)(`0x00`–`0x0F` / `0x40`–`0x45` / `0x59` / `0x60`–`0x63` / `0x7F`–`0xFA`)。
table base は各 band handler 冒頭の `lui v1,0x8012` + `addiu v1,v1,−N` ⇒ `0x80120000 − N`。

⚠ **band 表の外にも表がある**: `0x8011B020`–`0x8011B0F4`(35 slot が全て `0x800F0624`)/ `0x8011B264`–`0x8011B39C`(79 slot)。
これらは **sub-dispatch であり opcode 逆算に使ってはならない**。

### 3.1 entry の先頭表

各 entry は先頭に offset 表を持ち、その **byte 長 = 先頭 u16(`word0`)** が自己記述する。

- **最初の section は `word0` から始まる。** 全 225 entry で「section 表の 1 行目の offset == `word0`」(**母数 225 / 一致 225**)。
  ⇒ **`[word0, 4+word0)` は表ではなく body(script)**。
- ⇒ **先頭表の総量 = Σ`word0` = 7,136 byte**。
  ⚠ `8,036 byte`(= Σ(4+`word0`))と `7,963 byte`(= 7,136 + gap 実測 827)は **どちらも誤り**。
  前者は gap を表に入れた仮定、後者は **未決だった「gap は表か body か」を片側に決めた値**。

## 4. 退出規約 — `jr ra` ではなく longjmp

- BIOS `A(0x13)` = setjmp / `A(0x14)` = longjmp。
  番号付けは **corpus 内で検証済**(A-stub 22 件の被呼出署名 = memcpy 50 / printf 89 / strcpy 27 / strlen 25 …)。
- **longjmp call site = 36 site / setjmp = 2 site**(全数。materialize 検定で jalr 経路なしを確認)。
- 共通 epilogue **`0x800EF318`**(分岐元 67 site)= `a0 = 0x80164068 / a1 = 1 / jal longjmp`。
  ⚠ **合流点は 1 つではない。** band2 の exit `0x800ECA8C` も同形(`a1 = 1` の longjmp)。

router 側の帰結コード(setjmp の戻り値 `s1`):

| `s1` | 意味 | 動作 | site |
|---|---|---|---|
| 0 | 直接呼出 | opcode を fetch して dispatch | — |
| 1 | 正常完了 | `0x800F0764` へ = setjmp 張り直し → 次の opcode | 10 |
| 2 | VM 退出 | `0x800F0910` → 停止 flag を返して VM 関数を抜ける | 23 |
| 3 | 特別退出 | `0x800F3114` / `0x800F0CD0` 呼出 → `0x4B` を gp−27835 に書く → 退出 | 3 |

⚠ **`jal` の直後の命令が次の opcode の handler 入口である場合がある。**
物理的隣接を実行継続と読まないこと(実例: `0x800EE994` = op `0x67` 入口、表 `0x8011B3AC`)。

⚠⚠ **解析道具への帰結: 固定窓で PC 増分を合計する手法は band handler で壊れる。**
handler は `jr $ra` ではなく **longjmp で出る**ので、固定窓(例: 400 命令)は
**次の handler へ流れ込み**、返る値は「その opcode の長さ」ではなく **「band 末尾までの距離」**になる。
検出の署名: 導出値が **band 内で単調非増加**(128 / 111 / … / 4 / 1)かつ handler address が単調増加。
⇒ **窓ではなく `[表 entry, min(次 entry, 最初の longjmp))` で切ること**(§5 の handler 範囲規則)。

## 7. 台詞窓と再入(pending 状態機械)

- 台詞窓 = **`0x801640B8`、stride `0x34`、6 slot**。renderer `0x800F4200` が `a0 × 52 + base + 4` で index。
- **renderer は `pending := 0x1A` を書く**(`0x800F4BC0`: `addiu v0,zero,26` / `sb v0,-27836(gp)`)。
- ★実機観測: **`pending = 0x10` も立つ**(300 frame 中 31 が `0x1A`、**11 が `0x10`**)。
  ⇒ **CHOICE(`0x10`)も pending を立てる**。pending は `0x1A` 専用ではない。★
- router 冒頭 `0x800F0748`: `lbu pending` が **非 0 なら停止 flag を返して即退出** ⇒ 表示中は VM が保持される。
- pending の **clear(:= 0)= 28 site** / 非 0 書込 = 18 site(いずれも store 命令の数)。
- 停止 flag の **clear = 2 site のみ**: `0x800F0208`(初期化)/ `0x800F317C`。
  (全数根拠: displacement 全走査 + pointer 生成 0 件 + address の materialize 0 件。)

★**実機で決着(2026-08-12、60 秒 / 300 frame の連写)**★
- 停止 flag は **1 → 0 → 1 を 5 往復**(= 止まった VM は必ず動き出す)。
- しかし `0x800F317C` の条件 `(b & 0x0F) && (b & 0x40)` は **一度も成立していない**
  (実測値は `0x00` / `0xa0` / `0xa1` のみ。`0xa1` は `&0x0F` を満たすが `&0x40` を満たさない)。
- ⇒ **clear はすべて `0x800F0208` 由来**。この site は
  `pending := 0` / `gp−27835 := 0` / `gp−27832 := 0` / `gp−27828 := 0` / `停止 flag := 0` を**一括で行う初期化ブロック**。
- ⇒ ★**「停止した VM が再開する」のではなく、「新しい script が始まって初期化される」**★。
  `0x800F317C` の経路は実プレイ 60 秒で **0 回**。**主経路ではない**。
- ⇒ ∴ **停止 flag = その script の終了**。永久停止ではないが、**再開でもない**。

★**限定(この観測の射程)**★
- 観測は **フィールドでの会話 1 回・60 秒・1 場面のみ**。
  ⇒ `0x800F317C` が **他の場面(戦闘 / メニュー / イベント)で発火しない**ことは示していない。
  言えるのは ★**この場面では主経路ではない**★ まで。
- 時系列の対応(boss1): 停止 flag = 1 のとき `win0+14` = `0xa0`(200 frame)、
  flag = 0 のとき `0xa1`(44 frame) ⇒ **`bit0` が flag と逆相関してトグルする**。
  条件 `&0x0F` は `bit0` で満たされるが、**`&0x40` は 60 秒で一度も立たない**。
  ⇒ **観察であって解釈ではない: 「bit0 は動いている。bit6 は動いていない」**。
- PC が動くのは **flag = 0 の区間だけ**(flag=1 で 6 種 / flag=0 で 19 種)。
- call stack 深さ ≠ 0 は **最後の 1 区間(t=51.4–57.8)だけ**で、**entry 遷移(`0x93`→`0x94`)と同時**。
  ⇒ **入れ子は entry 遷移の区間でだけ起きている**。

| pending | 状態 |
|---|---|
| 0 | 通常実行 |
| `0x1A` | 台詞表示中(VM 保持) |
| `0x10` | **選択肢表示中**(実機観測) |
| `0x67` | **yield 中**(実機観測 2026-08-12、1 kHz trace)。§6 に `pending := 0x67` と書きながら**本表に載せていなかった** |
| `0xFF` | 再開経路が立てる印(実プレイ 60 秒で **未観測**) |

⇒ **yield ≠ terminate。** `0x1A` / `0x10` は停止 flag を書かない(全数確認)ので、次フレームに再入して続行する。

## 8. 走査の型(0 件を主張する前に、どれを走査したか書く)

1. displacement(gp 相対) 2. 絶対(lui+addiu) 3. **絶対は loop の 1 周目しか解けない**
4. pointer 生成(`addiu rX,gp,disp` を渡す) 5. register 経由(深さ N) 6. data 語
7. **近傍 base + 定数**(例: jmp_buf `0x80164068` + `0x50` = 台詞窓配列) 8. **stride 前進の署名**(`addiu rX,rX,0x34`)

⚠ **本 doc 内の全数値に型 3 の限定がかかる。**
`materialize 16 site`(台詞窓配列)/ `37 site`(jmp_buf)/ `36 site`(longjmp)/ `2 site`(setjmp・VM caller)は
いずれも **型 2(絶対)による計数 = loop の 1 周目のみ**。
`addiu rX,rX,stride` で回る 2 周目以降は見えていない ⇒ **すべて下界。要再走査**。
(型 1 = displacement による計数 — PC 62 site / pending 46 site / 停止 flag 5 site — には loop の影響はない。)

⚠ **さらに: 本 doc の全数走査は「感度」しか検証していない。**
materialize 検定は陽性対照(jmp_buf 37 / entity base 45 / band2 表 1)で **拾えること**を示したが、
**拾いすぎないこと(特異度)は一度も検めていない**。
⇒ `longjmp 36 site` / `materialize 16 site` / `setjmp・VM caller 2 site` は **上界の検証が未了**。
★**全数走査の申告は「見落とし」と「拾いすぎ」を別々に書く**★(出典: worker1 が偽陽性 3 件を申告しながら偽陰性 3 件が同時に出ていた実例)。

⚠ **用語の向きを固定する**(この定義が無かったため中継で反転した):
- **見落とし** = 拾うべきものを **拾わない** / 壊れた入力を **通す**
- **拾いすぎ** = 拾ってはいけないものを **拾う** / 正常な入力を **拒否する**

⚠ **「N/N」を書くときは、同じ行に「検めていない次元」を並べる。**
実例(worker2 の adapter、17/17): 検めたのは **存在の次元だけ**。見落とすのは
①値が壊れている ②行の順序 / 重複 ③別 savestate・別場面(header に場面情報が無い)
④**行が抜けている(原理的に検知不能)**。

## 8.1 「0 件」「N 件」を報告する様式(canonical)

> ⚠ この様式は 2026-08-12 まで **名前だけが流通し、本体が存在しなかった**。
> PRESIDENT が「5 点様式」と繰り返し呼び、boss1 がそれを中継し、worker1 が
> 「逐語を持っていない」と申告して発覚した。**名前を付けたら本体を書く。**

> ### 見出しの実例 — **(6-aq) 全数一致(13/13)でも意味は立たない**
> 2026-08-15。MAPHEAD id 1246 の命令 `0x4B` は operand として
> **168〜179 + 204 = 13 個**を持つ。これは町 **TWNA02〜13 + TWNA01 = 13 変種**と
> **要素も個数も完全に一致**した(部分一致でも偶然の一致でもない、**全数一致**)。
> それでも「`0x4B` = map 指定」は **④ 判らない**のまま据え置かれた。理由:
> `0x4B` の書き先 `[gp-0x6cac]` の sink を **EXE 全 177,664 語・全走査**で 6 件全部数え、
> - 読み手 2 件のうち `0x800F0378` は `sltiu 57` の表引き ⇒ **168〜179/204 は全部 57 以上 = この路は通らない**(1 本潰した)
> - 残る路 `0x800E3DA0` は map cell 家族(`[gp-0x6d8E]`→`[gp-0x6d8D]`)に触るが、
>   ★**名前表を索く索引 `[gp-0x6ca6]` は書かない**★
>
> ⇒ ∴ 立つのは「**operand 集合が 13/13 一致 / 経路が map cell 家族に触る**」までで、
> 「map を選ぶ命令」ではない。★**一致は、一致した次元についてのみ一致**((6-k)) の最強形★ —
> **数が完全に揃っているときほど意味を付けたくなる**。
> ⇒ ∴ 発見者(worker1)が**自分の発見に**この規律を当てて ④ を申告した。
> **規律は、発見者自身の手柄を削る向きに働いてはじめて効いている**。
> ⇒ ∴ 対になる実例(同日、worker2): data 側に見つけた `[1225, 1231, 1237, 1243, 1249]` は
> **公差 6 の等差**だったが「**座標の公算・私は決めません**」と留保した。**等差も意味の証拠ではない**。

1. **射程** — 何を、どの範囲で走査したか(母数を数値で)。
2. **再検定** — **別の走査型**でも同じ結果か(下の型リストから 2 つ以上)。
3. **陽性対照** — 検出器が動くことを示す実例。★**対象と同じ gate を通るもの**でなければ意味がない★
   (別 gate の対照で「検出力あり」と言うと、0 は依然として判定不能)。
   ⚠ 陽性対照が複数あって 1 つだけ 0 を返したら、**対象の 0 ではなく対照の失敗を先に疑う**。
   ⚠ **対照にも gate を併記する。** 対照と対象の gate が違えば比較にならない
   (実例: 緩和 gate が比較 `==` を write と拾い、対照側が偽陽性を出した。**対照はどちら向きにも失敗する**)。
4. **残る穴** — 原理的に検出できない範囲を明記。
5. **走査の型の列挙** — §8 のどれを使ったか(displacement / 絶対 / loop 2 周目 / pointer 生成 /
   register 経由 / data 語 / 近傍 base + 定数 / stride 署名 / 機械抽出)。

**さらに、報告する数がどちら向きでも:**

- **見落とし**(拾うべきを拾わない)と **拾いすぎ**(拾ってはいけないものを拾う)を**別々に数える**。
  片側だけの申告は健全性の証拠にならない(実例: 偽陽性 3 件を申告しながら偽陰性 3 件が同時に出ていた。
  **同一 bug の 2 症状**であって独立 6 件ではなかった)。
- ★**誤りの向きは gate の締め方で決まる**★ — gate を緩めれば拾いすぎ、絞れば見落とし。
  「全数走査は母数を大きく取る方向に誤りやすい」は**その道具の gate が緩かった場合の観察**であり、普遍則ではない。
- ★**「在りました」にも拾いすぎの対照を付ける**★。「0 件」は疑われるが、
  **数が出た時点で信じられてしまう**。
- 「N/N」を書くときは同じ行に **検めていない次元**を並べる。

**(6) ばらつかない結果は、向きに関わらず「測定側」を先に疑う**
3 者 + PRESIDENT が別々の向きから同一の型に到達したため独立項として立てる。

| 向き | 現象 | 正しい読み |
|---|---|---|
| 全部外れる | 要素数は合うのに**全件不一致**、ずれ幅が一定 | 対象でなく**対照**の失敗 |
| 全部揃う | 尾側 30 cell が全部 match | zero-order hold(**保持**)の疑い |
| 全部同じ値 | 4 つの異なる base で連続長が **201,201,201,201** | gate が緩く**弁別力ゼロ** |
| 全部ゼロ | `strings` が null-by-design すら 0 件 | **その道具に検出力が無い** |

⇒ **診断道具にも (3) を当てる。道具の検出力を先に検める。**
⇒ 「気づけた」は「次も気づける」ではない ⇒ **系統性の検査を対照の標準手順に置く**。

**(6-b) 誤りの軸は 2 つでは足りない — 第 3 軸 = 提示**
見落とし(拾うべきを拾わない) / 拾いすぎ(拾ってはいけないものを拾う) の他に
★**2 つの正しい数を間違って並べる**★ がある。見落とし 0・拾いすぎ 0 の**どちらでもない**。
(実例: 集計 script の表示バグで「pc の 87.6% が -1」→ 実は **99.9% が有効**。
 抽出も判定も正しく、**並べ方だけ**が誤っていた。)

**(6-c) 一致の主張と不一致の主張は非対称**
★**不一致の主張は部分でも立つ。一致の主張は全体でしか立たない。**★
- `exit 1`(差が在った) — 範囲が狭くても主張は倒れない。1 件見つければ「差が在る」は真。
- `exit 0`(差が無い) — 範囲が狭いと**偽になる**。見ていない範囲に差があれば主張は崩れる。

⇒ ∴ 両者を**対称に扱うと、どちらかが必ず誤る**。器の設計では
   「一致」を返す条件にだけ**全体到達**を要求する(例: `tail_gap == 0` のときだけ `exit 0`)。
⇒ ∴ これは率・カバレッジ・N/N すべてに効く。**「0 件」は範囲の申告なしには読めない。**

**(6-d) 情報を落とす向きの計器バグは「強い主張」を作る**
実例: 集計 key を 400 字で切り詰め、512 字の `vars` が潰れて「1 種」と誤答。
そのまま出れば ★「vars は検定力ゼロ」★ という**より強い(そして偽の)主張**になっていた。
⇒ ∴ **区別を潰す向きのバグは「0 件 / 一様 / 検定力ゼロ」を生む。** 雑音を足す向きのバグは主張を弱めるだけで、
   気づかれやすい。∴ **危険なのは前者**であり、それは**都合の良い結論の顔をして出てくる**。

**(6-e) 「無害」の測定には賞味期限がある(並走時)**
実例: PRESIDENT が「path はまだ壊れていない」と実測 → その数分後に別 agent が file を移動 →
**同じ path が壊れた**。測定そのものは正しく、**前提の方が動いた**。
⇒ ∴ 並走中の「今は無害」は**時刻つきでしか主張できない**。凍結を要求するなら**測定ではなく合意**で止める。

**(6-f) 「commit した」と「他者が読める」は別**
同時期に 2 件: PRESIDENT の doc 更新 21 件が `main` に無い / worker1 の doc が共有 repo で
v3-2(479 行)のまま止まり、v3-13〜v3-37 の 25 節が未収載だった(消費側は逐語転送だけが頼りだった)。
⇒ ∴ sha を報告するときは ★**収載側の sha も併記する**★(差があればその場で判る)。

**(6-g) 巻き戻しは道具 1 本では終わらない — 参照している側も同時に戻す**
実例: 移動を revert したが、adapter 側の path pin と sha pin は移動先を指したままで、
共有 repo の実体が消えた時点で**器が全部動かなくなっていた**。
⇒ ∴ 移動を発注した時点で**参照が増える**ことは判っていたはず。revert は**参照側を数えてから**。

**(6-h) 互換性を足すと、重なっていた防御が 1 枚に減ることがある**
実例: 欠けた語を許すため全 field を `.get()` で読むようにしたら、
それまで**存在検査を二重にしていた**下流の `KeyError` が消え、防御が gate 1 枚だけになった
(gate を殺すと**黙って通る**ようになり、「存在検査は二重」という過去の申告が偽になった)。
⇒ ∴ **足したときに「減った方」を数える。** 互換性は防御を薄くする方向に働くことがある。

**(6-i) 非同期系では「依頼」は制御ではない**
実例: 「保留をお願いします」が届いた時点で、送出は済み・移動は実行中だった。
⇒ ∴ **依頼は到着まで効かない。** 止めるなら**実体を動かす**(復元する / file を戻す)のが唯一確実。
   (6-e) と対: **測定でも依頼でも止まらない。状態を変えることだけが止める。**

**(7) 写しを作らない一般解 = 上位集合を取る**
比較 key を手写しすると片側が動いたとき静かにずれる。key を上位集合(例: t 以外の全 field)に
すれば写しが不要になり誤拒否も消える。同形で `IsInBand` は「機械化」でなく**撤去**で解ける
(runtime は op をそのまま出し、分類は EXE を読む解析側が持つ)。

**(7-b) 写しの循環は「証拠が弱い」ではなく「特定の欠陥が原理的に見えない」**
2 例が出た。性質が違う。

| | maps.json | walker の `Len[]` |
|---|---|---|
| 経路 | EXE → `map_entries.json` → `maps.json` | EXE → remake の shipped `Len[]` → walker |
| 一致が示すもの | transform が id↔name を保存した | **何も示さない** |
| 被害 | 証拠にならない(恒等式) | ★**remake の Len 誤りが walker にも入るので、その誤りが原因の差分は出力に現れない**★ |

⇒ ∴ 後者は「弱い証拠」ではなく **盲点**。器と対象が同じ誤りを共有すると、
   **その誤りに起因する非忠実性は構造的に検出できない**。
⇒ ∴ 現に shipped `Len[]` は **6 件が実測で誤り**(`0x39 0x73 0x74 0x77 0x7D` + `0x10` 可変)で、
   **可変 14 / band 外 151 は未検証**。∴ walker 由来の被覆率・命令数・TEXT byte は
   ★**この表の上に立っている**★ と併記しないと読めない。
⇒ ∴ remedy は (7) と同じ — **写しをやめる**。器は EXE から直に取るか、分類せず生で出す。

**(6-k) 一致は、一致した次元についてのみ一致 — 本 session の最頻の誤り**
同じ形が 1 日で 3 度出た。いずれも「一致した」を別の次元に読み替えている。

| 一致した次元 | 読み替えた先 | 反例 |
|---|---|---|
| 要素数 **105** | 集合の一致 | 境界が 1 ずれて相殺しても 105 |
| `maps.json` **244/244** | 独立確認 | 生成器が EXE 由来 ⇒ 恒等式 |
| offset 式(**引き方**) | 表の一致(**引かれる物**) | `_offsets` が 1 entry ずれた表でも式は完全一致 |

⇒ ∴ **最強形は §8.1 冒頭の (6-aq)**(13/13 全数一致でも ④ 判らない)。上の 3 例はいずれも
   部分一致・恒等式・別次元だったが、(6-aq) は**全数一致でも立たなかった**。
⇒ ∴ 「一致した」と書くときは ★**どの次元で一致したか**★ と ★**一致していない次元**★ を並べる。
⇒ ∴ 検算の相手を選ぶときは「同じ答えが出るか」ではなく
   ★**その相手は、私が間違っていたら違う答えを出すか**★ を先に問う(出さないなら検算になっていない)。

**(6-m) 打ち切った list から総数を読まない**
実例(PRESIDENT、2026-08-12): 他者の計数誤りを訂正する便で、自分は
`grep ... | tail -24` の出力を数えて「12 便」と報告した。**真値は 39 便**(#197-#235)。
`tail` が母集団を切っていたのに、切ったこと自体を数から落とした。
⇒ ∴ ★**総数を主張するときは `wc -l` を使い、表示用の `head`/`tail` を通した出力から数えない**★。
⇒ ∴ 訂正する側は**同じ検査を自分に当ててから出す**(訂正の便が最も緩む)。

**(6-q) 周辺分布が合うのに同時分布が退化していたら、標本ではなく変換を疑う**
「観測が 0 件」の原因が **到達不足(標本が少ない)** か **計器が別物(量が違う)** かを分ける判別子。

- **標本不足なら**: 支持集合は同じまま、件数だけが一様に薄くなる。
- **変換されているなら**: ★**周辺は合うのに、特定の組合せだけが厳密に 0**★ になる。

実例(2026-08-12): join の mode 分布で `bit 0x10` を含む合計は 38.30% 対 静的 35.33% と**ほぼ一致**。
しかし内訳は `0x18` のみで、`0x10` 単独・`0x30`・`0x38` が**すべて 0**。
`bit 0x20` 族は 67 件**全部が単独**(静的では単独は族の 47.2%)。
⇒ ∴ 到達の偏りではこの形は作れない ⇒ **観測側の `cond` は静的側の byte と同じ量ではない**。
⇒ ∴ 「予測が倒れた」を受け入れる前に、**支持集合の崩れ方**を見る。

⚠ **この判別子は「片方が壊れている」までしか言わない。**(2026-08-12 追記)
初出時、PRESIDENT と boss1 はどちらも**観測側(動的)の計器**を疑った。実際に壊れていたのは
**静的側の stride** だった(`mode 0x20` を一律 2 byte としたが、実長は `2 + StatOperandLen(cond&7)`
= **2/4/6/8**。最大 6 byte 進み足りず、operand を項頭として読んで **phantom join** を湧かせていた)。
⇒ ∴ ★**一方の器を疑った時点で、もう片方を免責している**★。疑うべきは**両方の器**。
⇒ ∴ 正しい順序(worker3 が実行した形): ★**自分の側の自己整合を先に示してから、相手を名指す**★
   (実例: `Σ(項数 × 式数) = 6,682` = term 総数と完全一致 / `mode 0x18 = 2,559` = 式総数 ⇒ 1 式に分岐項 1 本)。

**(6-r) 誤りの向きが分かっていれば、片側の 0 は結論になる**
`entry 178` の join は静的走査で **0 件**。静的 walker は **phantom を湧かせる = 過大に数える側**と判明した。
⇒ ∴ ★**過大に数える器が 0 を返したなら、真値も 0**★(逆に、過少に数える器の 0 は何も言わない)。
⇒ ∴ これは (6-c)「不一致は部分でも立つ / 一致は全体でしか立たない」と同じ非対称。
   **器の誤差の向きを先に決めれば、壊れた器からでも片側の結論は取り出せる。**
⇒ ∴ 現に join の総数(`315`/`31`/`6`)は全部引用停止だが、**「remake は join を一度も踏んでいない」は生きている**。

**(6-o) 「古い」と「出所不明」は別 — 前者は差し替え、後者は撤回しかない**
実例: ある doc は「Len 修正 3 件(`0x2c/0x39/0x73`)を当てた版」と書くが、
code の上書きは `0x74/0x7D/0x77` だった。⇒ **どの構成からも再現できない**。
| | 意味 | 処置 |
|---|---|---|
| 古い(stale) | 特定の旧版と一致する | 新版で**差し替え**できる |
| 出所不明 | どの版とも一致しない | ★**撤回しかない**★(差し替え先が存在しない) |
⇒ ∴ 「stale」と書く前に **どの版と一致するかを言えるか**を確かめる。言えないなら stale ではない。

⚠ **2026-08-12 追記 — 「出所不明」と判定する前に、まず探せ。** 上の `152` は後日
**完全再現した**(`variant E` で内訳・式数・per-entry まで一致)。真因は失われたのではなく
★**walker が 2 本あることは知っていたのに、どちらで出したかを記録していなかった**★ こと。
⇒ ∴ ★**「出所不明」の実体は、失われたのではなく書かれなかった**★。
⇒ ∴ remedy = **数の隣に「どの器で出したか」を書く**(値と器は一体)。

**⇒ ∴ 第 3 の型: 再現できるが、根拠のない設定に条件づいている**

| 型 | 判定 | 処分 |
|---|---|---|
| 古い(stale) | 特定の旧版と一致 | 差し替え |
| 出所不明 | どの版とも不一致 | 撤回 |
| ★**variant 依存**★ | **再現するが、機構の裏付けがない switch に条件づく** | ★**variant 併記の上でのみ引用可**★ |

実例: `152` は `variant E`(`ret_stop`/`far`/`f17` の 3 switch)で再現するが、
`base` では **208**。**38% の振れが解析者の選択で決まる**。
⇒ ∴ ★**結論は variant 全域で不変なものだけを引く**★(不変でないなら、検めた範囲を明記する)。
⇒ ∴ 「A を撤回したから B が残る」と書くとき、**B が同じ variant に乗っていないかを先に見る**。


**(6-s) 自責も claim — 母数と出典を添える。謝罪は検証を免除しない**
実例(2026-08-13): boss1 が「台帳の『6/6 一致』を自分が『8 個全部』と読み替え、
誤った通知をした」と自責したが、worker1 が commit を提示して**その自責が誤り**だと示した
(worker1 自身が事前登録で母数を 8 通りに訂正しており、boss1 の中継は正しかった)。
⇒ ∴ 我々は**正の主張**と**撤回**には出典を要求してきたが、★**自責は額面で通していた**★。
   自責は「安全側」に見えるぶん検証されない — worker2 の
   「弱く言う方向にも検証が要る」の**帰属版**。
⇒ ∴ ★**「私が誤った」と書くときも、どの commit / どの行を見て言うかを添える**★。

**(6-u) 器の 1 本が知っていることは、他の器が知っていることにならない**
