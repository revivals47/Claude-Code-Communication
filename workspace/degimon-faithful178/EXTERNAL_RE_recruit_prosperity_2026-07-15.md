## 3. 勧誘・繁栄度の仕組み（dg.scn レベルで確定）

各デジモンの加入イベントは dg.scn 内で**典型的に**次の3点セット
（例外あり: ヴァンデモンは定型文なし §4※、未捕捉分 §4 残課題）:

1. `0x1C SET_FLAG(固有フラグ)` — 加入の永続記録（bit store +0xF5）
2. `0x1F VAR_ADD(var=1, +点数)` — **繁栄度加算**（成長期+1 / 成熟期+2 / 完全体+3 / 汚物系+1）
3. 定型文 **「〇〇が街に参加した！！！」**（SJIS、フラグの±96B 以内）

→ remake 実装への示唆: 繁栄度は独立フィールドでなく**イベント変数バンクの var[1]**。
GameState に var バンクを実装すれば SET_VAR/VAR_ADD/VAR_SUB (0x1E/0x1F/0x20) の配線だけで
繁栄度システムが原盤忠実に動く。加入判定・街NPC出現は下表のフラグ read で足りる。

### opcode 0x75 = NPC スポーン（12B 固定、実RAM照合済み）

```
[0x75][char_id u8][x s16][y s16][z s16][dir s16][entity_flag u16]
```
- `entity_flag` はエンティティ表 +0x30 に格納される**対話/イベント状態フラグ**（≠加入フラグ）。
- 実証: slot3 の現在マップのエンティティ3体（グレイモン 0x2C2 / ベーダモン 0x2B3 /
  ティラノモン 0x2BA）が dg.scn 該当エントリの 0x75 オペランドと完全一致。
- DialogueRuntime.cs の長さ表 12（0x75、authority 実測 71/71）とも整合。

街 NPC ジジモンは加入デジモンごとに「〇〇がここに来てな…」という1行を持ち、

|---|---|---|

「私にくらべて部下はだらしないので、**スカルグレイモンを闘技場へ連れていっている**んだ」
「今のスカルグレイモンは以前と違って言うことを聞くやつだから安心してくれ」
= **ヴァンデモンが連れてくるスカルグレイモンが加入する**イベント。
近傍の「ヴァンデモン！」というテキストに引きずられたのが誤同定の原因。

**ヴァンデモンは勧誘対象ではない**: dg.scn に「ヴァンデモンがここに来てな」の
ジジモン台詞が**存在しない**（全文検索で0件）= 街の住人として加入しない。
攻略情報の「ヴァンデモンを仲間にする」は闘技場参加の意で、繁栄度加算は
スカルグレイモン加入として計上される。

**イベント形状**: 定型文「〜が街に参加した」を**出さない唯一の加入**。
`SET 0x81 / SET 0x10A / SET 0xE2` + VAR_ADD(+3)。0x81 は同エントリで多数の条件参照を持つ
**多段イベントの進行段階フラグ**で、連鎖（館地下でヴァンデモン発見→れいぞうこのカギ(item 0x56)
→オーバーデル墓地で血のしたたる肉(item 0x55)→ヴァンデモンに渡す→闘技場参加→シェル掲示板記事
→館でスカルグレイモン戦）の最終段で完了する。
→ **途中段階で止まると加入フラグは立たない**（実プレイでこの状態を確認）。
remake 移植時に「定型文なし」「多段ゲート」「名前とイベント主体の不一致」の三重で最難関。

（※さらに旧版で「消えた…まぼろし…？＝加入失敗の分岐」と記したのも**誤読**。当該テキストは
SET_FLAG 0xE2 の後方に位置し、加入可否の分岐ではない。訂正済み）

ジジモン台詞リストの gate 対応は独立かつ機械的な検証手段として有効 — 残る未同定フラグ
（0xD2/0xD6/0xFD/0xFE）と未捕捉分も、この手法で再検証すべき（残課題）。

### 会計（数の整合）と未同定（残課題）

捕捉（VAR_ADD(var1)∧SET_FLAG 近接）は **47フラグ・計93点**。内訳:
- 名前同定済み 43体 = **84点**（上表）
- 名前未確定 4フラグ = **9点**: **0xD2 (+2) / 0xD6 (+3) / 0xFD (+1) / 0xFE (+3)**
  （0xFD は下記の反復パターン構成要素のため勧誘フラグでない可能性あり・要精査）
- 未捕捉 = **≤7点**。ただしこの値は「最大値=100」という**外部前提からの逆算**であり、
  独立検証ではない（最大100自体の EXE 内根拠の特定は残課題）。
- 未割当のデジモン: デビモン・エアドラモン・メガドラモン・メタルグレイモン・もんざえモン・
  スカルグレイモン・ナニモン・シードラモン・ゲコモン（9体）。段階別点数則の期待和(22点)と
  未確定+未捕捉(≤16点)は一致しないため、**この中に繁栄度に寄与しない/別機構の個体が
  含まれる**とみられる。個体別の確定は 1体ずつのセーブ差分で可能。
- 別途 `[SET_FLAG 0x30][SET_FLAG 0xFD][SET_FLAG 0x14D〜0x151]` + VAR_ADD(var1,+1) の
  反復パターンあり（entry 46/79/105-108/138/192）。勧誘とは別系の繁栄度+1 イベントの可能性。要精査。

### 付随フラグ（勧誘イベントが加入フラグと同時に立てるもの）

live 差分で観測。**加入フラグと同一イベント内で set される別種の永続フラグ**であり、
remake が加入だけを実装すると取りこぼす。判明分:

| フラグ | 同時に立つ加入 | 判明した役割 |
|---|---|---|
| 0xAE | 0xFA コカトリモン | **同イベントの再出現ガード**。出現条件式 `!flag[0xAE] ∧ !flag[0xFA] ∧ var[107]∈[4,6]`（§付録A で独立デコード検証済）の第1項そのもの = 撃破/加入後に石像エリアへ再訪しても再発火しない |
| 0xE5 | 0xE9 ユニモン | ユニモンイベント進行系（役割未同定）|
| 0x257 | 0xE3/0xEF 同時勧誘時 | 未同定（永続帯）|
| 0x81 / 0x10A | 0xE2 ヴァンデモン（予定）| 加入時 3点セット `SET 0x81 / SET 0x10A / SET 0xE2` で立つ。0x81 は同エントリ内で多数の条件参照を持つ**連鎖イベントの進行段階フラグ**（§4※ 参照）|

→ **示唆**: 勧誘イベントは「加入フラグ + 繁栄度加算 + 再出現ガード/進行段階フラグ」の複合。
remake の勧誘実装では、加入フラグだけでなく**ガードフラグの set と、出現条件式での参照**を
セットで移植しないと、勧誘済み NPC がフィールドに再出現する。

## 5. 検証（各項目が何をどこまで検証するかを明記）

⚠️ 検証 1〜3 と 5 は同一の対応表・同一プレイ履歴に依存しており、**5本の独立検証ではない**。
それぞれの検証力の範囲を付記する。

1. **点数 checksum**: 捕捉47フラグ中、slot3(繁栄度87) で未設定のものの点数合計 =
   0xDC(2)+0xE2(3)+0xE3(3)+0xE9(2)+0xEF(1)+0xFA(2) = **13 = 100−87** ✅
   （§5-5 後の再計測でも 9 = 100−91 ✅）
   ※これは「フラグ集合と点数割当」の集計整合であり、**名前の入れ替えに対して不変**。
   個別の名前↔フラグ対応は検証しない（その根拠は §4 の定型文近接・コピー間一致）。
2. **時系列整合**: 全ステートを通じ加入フラグ帯は**単調にしか増えない**ことを確認 ✅
   （単調性は「永続進行フラグ」であることの傍証で、勧誘固有性までは示さない）
3. **プレイヤー申告との一致**: 「デジタマモン・エテモン・クワガーモンを最近勧誘した」
   → 0x100/0xF2/0xFB がいずれも resume(06/23)→slot3(07/14) 間で 0→1 ✅
   （集合レベルの一致。3体↔3フラグの内部置換はこの検証では排除されない）
   「ヴァンデモンも勧誘した(はず)」→ 0xE2 は全ステートで 0。§4 の非加入分岐と**整合**
   （ただしこれは反証テストでなく事後説明）
4. **エンティティ表照合**: slot3 現在マップの実 RAM エンティティ3体の +0x30 フラグが
   dg.scn の 0x75 オペランドと一致 ✅（0x75 構造の検証であり、加入フラグ表とは独立の主張）
5. **live 検証（2026-07-15）**: 対応表確定後、プレイヤーが実機でメタルマメモンと
   スカモンを新規勧誘 → slot3 再取得。勧誘フラグ帯の変化は **{0xE3, 0xEF} のみ**、
   繁栄度 87→91（+4 = 点数表の {+3,+1} と一致）✅
   ※2体同時の差分のため「どちらがどちらのフラグか」は**この実験単独では区別できない**
   （個別対応は §4 の定型文証拠による）。副次観測: 0x257 が set（勧誘に付随する別の
   永続イベントフラグ）、0x32B set / 0x32A clear（揮発帯）。
   **今後の live 検証は 1体ごとにステートを取り、予測フラグを事前記録**すること。
6. **live 単独検証①（2026-07-15、運用規則適用後の初例）**: 事前予測「ユニモン勧誘で
   0xE9 set・繁栄度+2」→ 実測 91→93(+2)、勧誘フラグ帯の変化は 0xE9 のみ ✅
   **1体単独差分のため、ユニモン=0xE9=+2 は個別レベルで実機確定**。
   副次: 0xE5 も同時 set（付随フラグ、§4 参照）。
7. **live 単独検証②（2026-07-15）**: コカトリモン勧誘 → 実測 93→95(+2)、勧誘フラグ帯の
   変化は **0xFA のみ** ✅ **コカトリモン=0xFA=+2 を個別確定**。
   さらに **0xAE が同時 set** され、これは §付録A で独立デコード済の出現条件式
   `!flag[0xAE] ∧ !flag[0xFA] ∧ var[107]∈[4,6]` の第1項 = **静的解析で予測した
   ガードフラグが、実機で予測どおりのタイミングで立った**（静的↔動的の直接照合）✅
8. **残余の確定（2026-07-15、繁栄度95時点）**: 名前未確定4フラグ（0xD2/0xD6/0xFD/0xFE）は
   **全て set 済み**。よって未設定の加入フラグは 0xDC(エンジェモン,+2) と 0xE2(ヴァンデモン,+3)
   の2つのみ、合計 **5 = 100−95** ✅ checksum が全 live 更新（87/91/93/95）で連続一致。
